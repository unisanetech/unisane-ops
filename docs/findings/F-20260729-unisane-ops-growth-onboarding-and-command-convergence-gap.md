## Summary

- Severity: `MUST`
- Status: `in-progress`
- Owner: `architecture-program`
- Target Pack: `P120`

## Symptom

The correct Ops product packages exist, but ordinary Growth adoption is distributed
across marketing, GTM, SEO, ads, analytics, and provider commands; app-local marketing
and GTM config; multiple auth/profile projections; manual resource ids; raw
access-token fallbacks; overlapping setup/status/doctor/proof state; and a Growth-owned
static console. The current console also exposes twelve flat mixed-purpose routes,
control-plane vocabulary, repeated warning/readiness cards, duplicated main/inspector
content, and no dedicated connection hierarchy. Proof counts, report-family counts,
provider pulls, artifact readiness, raw ids, receipt keys, filenames/paths, mutation
mechanics, planned providers, empty charts, unavailable values rendered as zero, and
unfiltered data rows appear because the system can expose them rather than because they
help the current user decide or act.

## Impact

Developers must understand implementation boundaries before receiving value, setup can
appear complete while instrumentation or data is not usable, provider access problems
are difficult to distinguish from config errors, and adding convenience wrappers would
leave two supported systems that can drift. Framework and non-Framework adoption is
possible in principle but not yet one predictable product workflow. Visually polished
screens still require users to interpret `proof`, report families, provider pulls,
mutation guards, readiness fractions, and repeated warning states before understanding
what happened or what to do. Research navigation wraps and overflows, Analytics is mostly
evidence diagnostics, GTM is a developer workflow, Recommendations lack impact/action,
Receipts expose machine artifacts, and Schedule omits expected automation controls.

## Fix Plan

1. Implement the decision-owned Ops adoption lifecycle and shared readiness/next-action
   model, beginning only at `unisane ops init`.
2. Move Growth intent into the one root config and provider access into one connection
   lifecycle.
3. Migrate every first-party project, test, document, and automation surface.
4. Delete all retired setup/auth/config/token/readiness/console paths in the same
   coordinated major-release workstream.
5. Complete instrumentation reconciliation, console separation, and team/CI credential
   lifecycle in later P120 workpacks without reopening parallel ownership.
6. In P120-W3, replace the flat control-plane navigation with the human-first
   capability/Connections/Activity hierarchy, consistent page anatomy, plain-language
   states, progressive technical disclosure, and direct accessibility proof.
7. Apply the four-question content-admission test and delete duplicate, irrelevant,
   misleading, unavailable, or unactionable presentation instead of relocating it all.
8. Add the final onboarding, sidebar, page/tab, Activity, Automations, tooltip/popover,
   table/chart, empty-state, and first-time-user comprehension contracts.
9. Delete the old routes and embedded presentation without an expert-mode dashboard,
   old shell, or presentation fallback.
10. Implement the exact SEO Overview/Opportunities/Pages/Queries/Site health/Research
    ownership, table/drill-down/state/copy contracts, and remove duplicate Search
    performance/Keywords navigation.
11. Implement one provider-card Connections index, independently truthful Google
    service rows, supported-provider-only availability, a full connection detail page,
    incremental grants/resource confirmation, and explicit disconnect consequences.
12. Apply the delete-first hard-replacement protocol to every bounded slice and block
    the next slice until old exports/routes/owners, consumers, tests, docs, config,
    assets, and generated residue are zero without an allowlist.
